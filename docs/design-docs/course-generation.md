# Goal-based course generation contract

## Scope and status

CN-COURSE-001 / [THE-16](https://linear.app/the-curious-tech-girl/issue/THE-16/generate-validated-goal-based-demo-course-plans), authorised M2 preview. English only. The two subject catalogues remain draft. Personalised titles, context and introductions are proposals, not subject approval. No model-generated lesson, rubric, achievement or qualification. M1/M1.5 release gates remain open.

## Generation and integrity

Save goal/preferences as an immutable revision. Ask Groq through a server adapter for structured classification and a proposal. Each proposal belongs to one subject. Recognised AI-plus-account/security keywords trigger a deterministic clarification. A recognised single-subject clarification constrains the next proposal. This guard is narrow, semantic interpretation still requires evaluation. Obvious introductory email/study-note/phishing/account-protection goals pin the allowed intent and output state in the request schema. Other goals retain model interpretation with validation. Course context is generated live, not substituted with a fixed course. Validate recognised intent, literal goal evidence, bounded plain text, known/unique objectives, prerequisite closure/order and full intent-required coverage. Attach source and rubric version references from the server catalogue, never the model. Unsupported claims, unknown fields or invalid references fail closed. Lexical claim checks supplement a constrained outcome/template and are not a semantic correctness guarantee. Live evaluation remains required.

The provider receives only goal, optional clarification, explanation preference, session budget, English availability and the bounded catalogue. No learner ID, email or history. AI_PROVIDER must be groq. Missing GROQ_API_KEY or GROQ_MODEL produces an honest unavailable state. No default model or fixed-course fallback. Groq Chat Completions strict JSON-schema output still requires handling refusal/incomplete results and domain validation. [Official source](https://console.groq.com/docs/structured-outputs).

## HTTP and persistence

PUT /api/profile/goal accepts goalText (10-1000 characters), explanationLevel (very-simple/beginner/standard/technical), teachingLanguage (en), sessionMinutes (10/20/40), version (0 initially), and optional clarification (up to 500 characters). Returns saved snapshot. GET on the same route restores the current snapshot and most recent plan. Existing equivalent writes at the expected prior revision return the saved snapshot, conflicting edits return 409.

POST /api/course-plans accepts goalId and Idempotency-Key. GET /api/course-plans/:id retrieves an owned saved result. State is generating, clarification, unsupported, ready-preview or failed. Accept with POST /api/enrollments { planId }, Idempotency-Key. Enrollment response carries the saved proposal and diagnostic choice. POST /api/enrollments/:id/placement accepts { mode: skip } or { mode: diagnostic, diagnosticVersion, answers: [one option ID per selected objective] }. GET /api/enrollments/:id/diagnostic returns draft scenario questions without answer keys. The diagnostic answers and recommendation remain stored. { mode: beginning } saves a separate learner-selected starting objective, preserving the diagnostic result. Returns provisional placement only. Preview diagnostic is a provisional objective-based check, not a calibrated ability test. Historical self-reported placements remain unchanged. See [entry acceptance](course-entry-acceptance.md) for preferences, restoration and recommendation contracts.

All routes derive owner from verified session, enforce same-origin mutations, bounded JSON bodies, no-store responses and inaccessible-ID 404. Plans store immutable goal and catalogue snapshots, model/prompt configuration, generation attempts and a time-bounded lease. Unique owner/request keys and compare-and-set lease completion prevent duplicate calls/results across concurrent retries. Failed/stale attempts can be retried at most twice per plan, with durable per-learner generation limits. There are no fire-and-forget jobs. Browser reload resumes saved state and can explicitly retry expired work. Provider/configuration changes preserve ready plans. Retrying a failed proposal under changed settings returns 409 and directs the learner to create an updated proposal. Acceptance is transactional and idempotent, preserving existing enrollments/history. No database migration is applied to live services by this slice.

## Preview UX and acceptance

Authenticated /onboarding offers goal/preferences, restored drafts, generation status, one clarification, unsupported alternatives, proposal review, acceptance and optional placement/skip. Changes to goal create a new plan without changing an accepted enrollment. Session expiry preserves only confirmed server state. Errors retain current typed input. Unavailable language is explicit, no silent fallback. No unreviewed language release. Focus new state headings, label controls, keep status announcements polite and render model text inert.

Verify customer emails/study notes, phishing/account protection, vague/mixed goals, unsupported subjects, altered standards, missing prerequisites, injection, refusal, incomplete output and outages. Test goal revisions, retries/concurrent leases/acceptance, ownership, persisted reload and diagnostic no-evidence behavior. Record synthetic vs live tests separately. Live demo requires configured model/key and goal-to-plan evaluation. Model configuration is mandatory operator input, not chosen by an implementer fallback. Groq 429 responses become explicit retry-later failures, without automatic fallback.

Local browser checks used actual React components and HTTP/domain/store code with synthetic generator output and PGlite. Checked 320px/1440px, goal editing with changed coverage, saved reload without regeneration, enrollment/skip, keyboard focus and doubled body text. [Mobile capture](../design-artifacts/course-generation/onboarding-320.png), [desktop capture](../design-artifacts/course-generation/onboarding-1440.png). Browser authentication was a test adapter. These are not hosted, screen-reader or live-model acceptance.

Run the opt-in fictional-goal evaluation with Node.js 24: `node --import ./node_modules/tsx/dist/loader.mjs scripts/evaluate-course-generation.mts --live`. It loads ignored .env.local, sends nine bounded requests paced 30 seconds apart, and writes validated plans or neutral error codes plus public fictional inputs to [evaluation results](../design-artifacts/course-generation/groq-evaluation.json). CI never runs it. Domain checks require manual semantic review and do not establish model accuracy from nine samples.

Targeted checks preserve their configuration/timestamp: [mixed-goal correction](../design-artifacts/course-generation/groq-evaluation-mixed.json) and [constrained email intent](../design-artifacts/course-generation/groq-evaluation-customer-email.json). Final nine-case results use the current generator configuration. Review wording, not only JSON shape.
